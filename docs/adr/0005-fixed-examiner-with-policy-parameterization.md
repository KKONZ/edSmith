# Fixed Examiner Pattern with Policy Parameterization

The Examiner uses a fixed single-pass generation pattern — one LLM call per component per essay, with no council, no critic, and no architecture switching between iterations. The behavior of each pass is fully controlled by `PromptPolicy` (format and style) and `StrategyGuidance` (information environment). The Chief Examiner can change any of these fields when proposing updates, giving the system an expressive action space without changing code.

**Why a fixed pattern:** A variable-architecture search space (single agent vs. council vs. hybrid) is harder to diagnose and compare than a fixed architecture with parameterized behavior. When accuracy changes across iterations, a parameterized system lets the Chief Examiner attribute the change to a specific field change. An architecture switch confounds interpretation — it is unclear whether a council improved performance or whether the prompt changed in a correlated way. Fixing the architecture isolates `PromptPolicy` and `StrategyGuidance` as the sole sources of inter-iteration variation.

**Why not a council:** A Generator → Critic → Chair pipeline multiplies per-essay latency by 3× with no guarantee of improvement on scoring calibration. The Chief Examiner performs the quality gate at the iteration level instead — one call per iteration against all Feedback at once, with full access to metrics and iteration history. This is a more informed check than inlining a critic into every per-essay call.

**Consequences:** Inter-iteration changes are always attributable to `PromptPolicy` or `StrategyGuidance` field changes, making them auditable and reversible. The behavior space is bounded and enumerable — the Chief Examiner's proposals can be validated against the schema before applying them. Adding a new behavioral dimension means adding a field to an existing model, not adding an agent class.

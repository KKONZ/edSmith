# Chief Examiner Agent

Diagnoses feedback quality from the Examiner pass, produces a `DiagnosticReport` and `HumanReviewProposal`, and waits for human approval or rejection before the next iteration begins.

## Purpose

The Chief Examiner is the quality-control gate between iterations. It receives the feedback parquet the Examiner wrote, the Scorer's evaluation metrics, and the full history of prior proposals. It produces a diagnosis of what went wrong this iteration and proposes targeted changes to `StrategyGuidance` and `PromptPolicy` for the next one.

Nothing changes in `SessionState` until the human calls `approve_proposal`. Rejecting a proposal stores the critique without modifying policies or strategy, then a revised proposal is generated by re-running `run_chief_examiner` with the critique attached.

## Session Context

The Chief Examiner is invoked after:
1. `run_examiner_pass` has written `feedback_iter{n}.parquet`.
2. The Scorer has been trained and evaluated — `metrics_iter{n}.json` must exist on disk.

If either file is missing, `run_chief_examiner` returns an `error` dict rather than a proposal. Check the return value before proceeding.

## MCP Tools

### `run_chief_examiner`

```
run_chief_examiner(session_id: str, iteration: int, critique: str | None = None) -> dict
```

**What it reads:**
- `{drive_path}/sessions/{session_id}/feedback_iter{n}.parquet` — Examiner output
- `{drive_path}/sessions/{session_id}/metrics_iter{n}.json` — Scorer evaluation metrics
- `{drive_path}/sessions/{session_id}/proposals/iter{0..n-1}.json` — prior proposals (for history)
- `{drive_path}/sessions/{session_id}/state.json` — current policies and strategy

**What it writes:**
- `{drive_path}/sessions/{session_id}/proposals/iter{n}.json` — new `HumanReviewProposal` (status: `"pending"`)

**`critique`**: Pass when re-running after a rejection. The critique is included verbatim in the LLM prompt as "Human Critique of Previous Proposal" and must directly shape the revised proposal.

**Return value on success:**

| Field | Meaning |
|---|---|
| `session_id` | Session identifier |
| `iteration` | Iteration this proposal covers |
| `status` | Always `"pending"` on first call |
| `diagnostic_summary` | Concise human-readable diagnosis of the main issue |
| `per_component_issues` | Dict mapping component key → issue description |
| `proposed_strategy` | Full `StrategyGuidance` dict (all fields, not just changes) |
| `proposed_policies` | Dict mapping component key → `PromptPolicy` dict (only changed components) |
| `proposal_path` | Absolute path to the saved proposal JSON |

**Return value on error:**

```json
{"error": "Feedback parquet not found ..."}
{"error": "Metrics file not found ..."}
```

Do not call `approve_proposal` or `reject_proposal` if the return value contains an `error` key.

---

### `approve_proposal`

```
approve_proposal(session_id: str, iteration: int) -> dict
```

Applies `proposed_policies` and `proposed_strategy` from the pending proposal to `SessionState`, increments `iteration` to `n+1`, and marks the proposal as `"approved"` on disk. This is the only operation that advances the session.

**Return value:**

| Field | Meaning |
|---|---|
| `session_id` | Session identifier |
| `approved_iteration` | The iteration just approved |
| `next_iteration` | New `state.iteration` value (approved + 1) |
| `updated_policies` | Full `PromptPolicy` dict per component as now stored in state |
| `updated_strategy` | Full `StrategyGuidance` dict as now stored in state |

After `approve_proposal`, call `run_examiner_pass(session_id, next_iteration)` to begin the next iteration.

---

### `reject_proposal`

```
reject_proposal(session_id: str, iteration: int, critique: str) -> dict
```

Marks the proposal `"rejected"`, stores the critique string, and leaves `SessionState` unchanged. Does not advance the iteration counter.

After rejecting, re-run:

```
run_chief_examiner(session_id, iteration, critique="<your critique>")
```

The critique is appended to the LLM prompt and must be addressed in the revised proposal. If the revised proposal is also unsatisfactory, reject again with a more specific critique.

---

## Interpreting the DiagnosticReport

### `diagnostic_summary`

A concise description of the primary feedback quality issue this iteration. Typical diagnoses:

- **Score compression** — predicted Scores cluster in a narrow band (e.g., 5.5–6.5 for all essays); the Examiner is not discriminating between band levels.
- **Component-level miscalibration** — one component's mean score diverges from others; usually indicates the policy for that component needs re-targeting.
- **Over-prediction / under-prediction** — `smd` (standardized mean difference) > +0.5 means consistent over-prediction; < −0.5 means consistent under-prediction.
- **Missing evidence** — feedback text describes general patterns without citing specific essay content; `evidence_required` may need enabling.
- **Discourse blindness** — coherence Scores are uncorrelated with transition word usage or paragraph structure; enable `use_discourse`.

### `per_component_issues`

One issue description per component key. An empty string means the Chief Examiner found no specific issue for that component. Focus attention on components with non-empty issues before approving.

### `proposed_strategy` and `proposed_policies`

The proposed values are fully merged onto the current state — they represent complete replacement values, not diffs. When reviewing:
- `proposed_strategy`: look for newly enabled linguistic tool flags and `per_component_focus` entries — these add cost and latency to every `run_examiner_pass` call.
- `proposed_policies`: compare `proposed_policies[component]` against the current policy for each component with an issue. Only changed components are included in the return dict, but `approve_proposal` writes all four components.

## Record-Level Inspection

The Chief Examiner receives a sample of individual feedback records from the feedback parquet as part of its diagnostic context. Each record shows:

```
[component | predicted=6.5 reference=5.0 Δ=+1.5 confidence=low]
The essay demonstrates adequate task achievement with a clear position...
```

| Field | Meaning |
|---|---|
| `predicted` | Band Score the Examiner assigned to this component |
| `reference` | Ground-truth band Score from the IELTS dataset |
| `Δ` | `predicted − reference`; positive = over-prediction, negative = under-prediction |
| `confidence` | Examiner's self-assessed confidence (`high` / `medium` / `low`) |

Records are sorted by largest `|Δ|` per component, so the most anomalous cases appear first. This is the primary signal for identifying what the Examiner got wrong and why.

### Diagnostic patterns to look for

**High |Δ| with `confidence=high`** — The Examiner is confidently wrong. The feedback text likely does not contradict the assigned score, meaning the prompt is steering the model toward the wrong calibration anchor. Candidate fixes: raise `specificity`, enable `contrastive_anchoring`, add a `per_component_focus` correction, or add `additional_instructions` that re-anchor the score range.

**High |Δ| with `confidence=low`** — The Examiner is uncertain and guessing. The feedback text may contain hedging language or describe mixed signals. Candidate fixes: enable the relevant linguistic tool (`use_grammar`, `use_complexity`, etc.) so the Examiner has objective data to resolve the uncertainty.

**Small |Δ| but feedback text does not justify the score** — The Examiner is accidentally well-calibrated (score matches reference) but for the wrong reasons. The feedback text may be generic or describe a different component's features. Set `evidence_required: true` or increase `specificity`.

**Consistent sign on Δ across all records for a component** — Systematic over- or under-prediction for that component. Check `score_distributions[component].mean` in the `ExaminerSummary` from the prior `run_examiner_pass`. If the mean diverges from the dataset's average band (≈ 5.5–6.0), propose a recalibration via `additional_instructions`.

**Δ near zero for most records but one or two extreme outliers** — Likely noisy individual essays (very short, non-native, off-topic) rather than a systemic policy problem. Note in `per_component_issues` but do not propose a policy change based on outliers alone.

The 12-record sample (3 per component) is a diagnostic window, not the full dataset. Use it to form a hypothesis, then confirm against the aggregate `score_distributions` and val metrics before proposing changes.

## When to Propose Strategy Changes vs. Policy Changes

**Propose a strategy change** when the Examiner is missing information it needs to produce accurate Scores:
- Enable `use_grammar` when `grammar` component Scores are poorly correlated with error counts visible in the raw text.
- Enable `use_complexity` when `coherence` or `lexical` Scores show low variance and the feedback text does not mention sentence structure.
- Enable `use_discourse` when coherence Scores are high for essays that lack clear paragraph structure or transition markers.
- Enable `use_aoa` when `lexical` Scores do not reflect vocabulary sophistication differences between essays.
- Set `contrastive_anchoring: true` when Scores compress — anchoring forces the LLM to reason about the band boundary, which spreads the distribution.
- Set `per_component_focus` when a component needs a specific emphasis this iteration (e.g., `"grammar": "Pay close attention to article usage and subject-verb agreement"`).

**Propose a policy change** when the Examiner has the right information but the feedback text is ill-formed or the scoring is inconsistent in format:
- Raise `specificity` (toward 5) when the feedback is too terse to be useful as a training signal.
- Set `evidence_required: true` when feedback text makes claims not grounded in specific essay passages.
- Change `feedback_granularity` to `"both"` when overall writing quality observations are needed alongside component-specific ones.
- Add `additional_instructions` for a targeted correction the Chief Examiner identified (e.g., `"Do not award 7.0 or higher unless the essay demonstrates C1-level grammatical control throughout"`).

**Limit changes to 2–3 per iteration.** The Chief Examiner's system prompt enforces this. If a human critique asks for more changes than this, prioritise the highest-leverage fix and note the others as deferred to the next iteration.

## Test Set Purity

The Chief Examiner receives only aggregated test statistics (`test_accuracy`, `test_qwk`, etc.) — never individual test records. This is intentional: individual test-set inspection would contaminate the held-out evaluation. Do not attempt to pass individual test records to `run_chief_examiner`; the tool enforces this by only reading the summary dict from `metrics_iter{n}.json`.

Individual validation records are available via the feedback parquet (which contains validation essays) and may be inspected when diagnosing component-specific issues.

## Rejection and Critique Handling

When the human disagrees with the Chief Examiner's proposal:

1. **Call `reject_proposal(session_id, iteration, critique="...")`** — stores the critique, marks proposal rejected, leaves state unchanged.
2. **Formulate a specific critique.** Vague critiques ("this doesn't look right") produce weak revisions. Effective critiques name the component, the change you disagree with, and what you want instead:
   - `"Do not enable use_grammar — the grammar tool output is too noisy at the moment. Focus only on policy changes for the grammar component."`
   - `"The proposed coherence focus is correct but the specificity increase for task_response is wrong — leave task_response policy unchanged."`
3. **Re-run `run_chief_examiner(session_id, iteration, critique="...")`** — the critique is included in the LLM prompt and must directly inform the revision.
4. Review the revised proposal. Approve or reject again as needed.

There is no limit on the number of rejection cycles per iteration. The iteration counter advances only on `approve_proposal`.

## Typical Call Sequence

```
1. run_examiner_pass(session_id, iteration)         # Examiner writes feedback parquet
2. [train Scorer via Colab — writes metrics_iter{n}.json]
3. run_chief_examiner(session_id, iteration)         # diagnose + save proposal
4. [human reviews diagnostic_summary and proposed changes]
   → approve_proposal(session_id, iteration)         # advance to next iteration
   → reject_proposal(session_id, iteration, critique)
     → run_chief_examiner(session_id, iteration, critique=...)
     → approve_proposal(session_id, iteration)       # when satisfied
```
